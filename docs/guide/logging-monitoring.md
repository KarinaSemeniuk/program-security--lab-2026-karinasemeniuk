# Журнали і моніторинг

HttpTelemetry реєструє завершені запити як JSONL у var/log/audit.jsonl. Поля: time у UTC, level, event, requestId, actorId, objectId, sourceIp, method, route, status, durationMs, code. requestId створює сервер і повертає в X-Request-ID. Після автентифікації actorId береться з перевіреного облікового запису; до цього значення anonymous. objectId містить UUID із маршруту, якщо він є. Журнал охоплює входи, відмови, читання, адміністративні дії, бронювання й помилки. Запис завершення HTTP не доводить повну успішність зовнішніх побічних дій поза запитом.

Рівні: INFO для успіху, WARNING для 4xx, ERROR для 5xx. Шляхи невідомих маршрутів замінюються на unmatched. Не записуються body, query, cookie, Authorization, email, пароль, відкриті нотатки та ключі. Коди помилок беруться з внутрішнього реєстру. Користувач без чинного сеансу залишається anonymous.

Файл створюється з правами 0600 у каталозі 0700. Ротація після 5 MiB; зберігаються 5 завершених файлів і поточний. Це обмеження за обсягом, а не гарантія строку зберігання. Оператор архівує важливі журнали інцидентів окремо. Помилка запису виводить безпечне повідомлення у stderr і враховується лічильником.

Вікно моніторингу 60 секунд, до 10000 останніх запитів у пам'яті. Поріг: 5 невдалих входів або 3 серверні помилки. Подія monitor.threshold записується не частіше одного разу на хвилину. scripts/monitor-logs.mjs показує кількість запитів, невдалих входів, 5xx, p95 часу відповіді й порогові сповіщення. GET /health перевіряє доступність процесу; він не є доказом доступності всіх залежностей. Повну працездатність перевіряють функціональні проби.

Успішні POST додатково формують криптографічно пов'язаний журнал var/audit/events-chain.jsonl. Перед кожним додаванням перевіряються всі записи. Він призначений для одного процесу-письменника; запуск декількох API з одним файлом не підтримується. Тривалі журнали слід архівувати з довіреним checkpoint. Втрата можливості дописати ланцюг формує ledger.write-failed. Цей навчальний аудит після завершення HTTP не є транзакційною чергою подій БД.
