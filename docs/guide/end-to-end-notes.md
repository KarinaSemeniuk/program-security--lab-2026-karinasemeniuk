# Наскрізно зашифровані нотатки

Новий тип даних доповнює попередні серверні приватні нотатки. Кінцевими вузлами є пристрої одного власника бронювання. Браузер генерує AES-256 ключ і 96-бітний випадковий nonce для кожного збереження. Web Crypto виконує AES-GCM із 128-бітним тегом. Ключ зберігається лише в оперативній пам'яті та у завантаженому користувачем файлі відновлення. Сервер не отримує ні ключа, ні тексту.

AAD містить version, algorithm, keyId, ownerId, bookingId, revision у фіксованому порядку JSON. keyId — перші 128 біт SHA-256 ключа, відкритий відбиток. Нове збереження використовує revision+1. Сервер звіряє envelope із поточним користувачем, UUID маршруту та очікуваною версією, перевіряє формат і розмір. Він не може перевірити GCM-тег без ключа; цю перевірку виконує кінцевий клієнт. Текст відображається тільки після успішного decrypt.

Маршрути GET і POST /api/bookings/:id/sealed-note доступні лише власнику, адміністратор не має обходу. POST приймає envelope і revision. Історія конвертів зберігається в sealed_notes; блокування booking row і первинний ключ (booking_id,revision) запобігають втраченим оновленням. Унікальність (key_id,nonce) контролює повтор nonce у збереженій історії. Старі версії не розкриваються цим API.

Перенесення: користувач завантажує файл ключа, переносить його через довірений канал і імпортує на іншому пристрої. Файл не слід надсилати разом із шифротекстом через недовірений канал. Після закриття редактора ключ видаляється зі стану компонента; JavaScript не гарантує фізичне занулення пам'яті. При втраті ключа сервер відновити текст не може. Для нового ключа наявний текст спочатку відкривають старим ключем на довіреному пристрої; автоматична ротація або обмін ключами через сервер не реалізуються.

TLS залишається необхідним. Модель довіряє кінцевим пристроям і доставленому клієнтському коду. Вона не приховує власника, розмір конверта, час і номер версії та не забезпечує forward secrecy. Сервер, який підміняє клієнтський JavaScript, може атакувати кінцевий вузол; контроль доставки клієнта залишається окремою межею довіри.

FileHashChain зв'язує службові події SHA-256. Блок містить index, time, data, previousHash, hash. Початковий previousHash дорівнює 64 нулям. Ключі data сортуються; хеш охоплює весь блок без поля hash. Зміна даних/порядку виявляється перевіркою. Локальний ланцюг не має консенсусу чи PoW. Власник усіх файлів може переписати всю історію; для виявлення такого переписування checkpoint з кількістю блоків і head потрібно зберігати поза керованим сервером.
