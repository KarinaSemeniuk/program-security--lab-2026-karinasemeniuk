# Резервування відновлення і підтримка версії 0.2

## Склад і стратегія копіювання

Щоденна повна логічна копія PostgreSQL у custom-форматі pg_dump. Вона включає користувачів, ресурси, бронювання, сеанси, серверні й E2EE конверти та таблицю міграцій. Разом копіюються робоче оточення, серверний keyring нотаток, ліцензія, відкритий ключ видавця і ланцюг аудиту. Клієнтські E2EE ключі резервує сам користувач окремо: їх немає на сервері. Закритий ключ видавця ліцензій належить окремому видавцю й повинен мати власну незалежну копію.

Код і lock-файли входять у версійний реліз. node_modules, dist, кеші та тимчасові результати повторно відтворюються й окремого щоденного копіювання не потребують. Важливі журнали інцидентів архівуються оператором незалежно від циклічної ротації.

План: щодня о 02:00 Europe/Kyiv, 14 останніх щоденних копій у сховищі з правами 0700, ще одна копія на від'єднаному носії або окремому сховищі. RPO не більше 24 годин, RTO не більше 15 хвилин для навчального встановлення. Це цільові показники, які перевіряють на актуальному обсязі БД. SHA-256 у manifest контролює цілісність файла; AES-256-GCM додатково автентифікує зашифровану копію. Ключ резервування: 32 випадкові байти у hex-файлі з правами 0600, поза каталогом застосунку й резервними копіями. Втрата цього ключа унеможливлює відновлення копії.

## Відтворювана процедура

1. Задати BACKUP_KEY_FILE, DATABASE_URL та шляхи робочих матеріалів.
2. node --env-file=.env scripts/backup.mjs create /окреме-сховище/roombook-YYYYMMDD.rbbackup
3. node --env-file=.env scripts/backup.mjs verify /окреме-сховище/roombook-YYYYMMDD.rbbackup
4. Перенести копію і manifest у незалежне сховище; перевірити там SHA-256 і доступність ключа для аварійної команди.
5. Для відновлення задати RESTORE_DATABASE_URL на окрему БД з ім'ям roombook_restore_* або roombook_drill_*. Виконати scripts/backup.mjs restore <копія> <порожній-каталог>. Існуюча тестова БД вимагає --replace-test-database. Сценарій навмисно не дозволяє випадково перезаписати робочу БД.
6. Використати відновлені runtime.env, note-keys.json, installation-license.json, license-public.pem, events-chain.jsonl. В оточенні відновленого сервера явно задати URL цільової БД та відповідні шляхи; секрети не виводити в журнали.
7. Перевірити /health, вхід, каталог, свої бронювання, читання нотаток, чинність ліцензії та доступ до відновленої інформації. Сеанси за потреби відкликати після інциденту. Оцінити фактичну втрату даних і тривалість простою.

Копіювання БД й файлових матеріалів виконується послідовно. Для узгодженого відновлення на час копіювання зупиняють нові операції запису та ротацію ключів. Тестова процедура виконується на окремій базі. У промисловому середовищі потрібне узгоджене вікно або інший механізм знімка.

## Локальний реліз

scripts/prepare-release.mjs формує roombook-0.2.0.tar.gz і SHA-256. Архів містить зібрані backend і frontend, схему/міграції, зафіксовані залежності, документацію та службові сценарії. .env, .secrets, користувацькі дані, тестові облікові записи, журнали й навчальні fixtures не входять до релізу. Backend source maps виключаються; frontend source maps вимкнені. Команда повторного складання: node scripts/prepare-release.mjs <каталог>.

Встановлення: Node 22, npm 10, PostgreSQL 16; npm ci, npx --no-install prisma generate, налаштування оточення, застосування міграцій через npx --no-install prisma migrate deploy, створення нового локального keyring і отримання ліцензії від видавця. API прив'язаний до loopback; публічний доступ надає HTTPS reverse proxy. NODE_ENV=production і точний HTTPS CORS_ORIGIN обов'язкові. Приклад .env.example не є робочим секретом.

## Оновлення і довгострокова підтримка

Підтримувана гілка 0.2.x до 22.05.2027; 0.1.x оновлюється міграцією на 0.2.x. Перевірка npm audit для backend і frontend — щотижня та перед кожним випуском; повідомлення безпеки постачальників Node, PostgreSQL і залежностей перевіряються разом із ними. Критичні вразливості оцінюються після виявлення, виправлення проходить аналіз впливу, тести та пробне розгортання.

Перед оновленням створюють і перевіряють резервну копію. Оновлення спочатку встановлюють на тестове середовище з копією БД, запускають тести й основні користувацькі операції. Лише після цього замінюють робочий артефакт. SHA-256 звіряють до розпакування. Версії залежностей зафіксовані lock-файлами; небезпечні несумісні оновлення не застосовують автоматично.

При збої повертають попередній артефакт, якщо схема БД сумісна. Після несумісної міграції відновлюють БД, конфігурацію та ключі з перевіреної копії; можливу втрату нових змін оцінюють за RPO. Старі версії завершують підтримку після повідомлення користувачів і надання шляху міграції. При виведенні з експлуатації експортують потрібні дані, відкликають ключі/сеанси, закривають службові облікові записи й мережевий доступ.
